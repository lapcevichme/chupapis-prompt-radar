# Prompt Radar (Промпт-радар)

Аналитика запросов к корпоративным ИИ-агентам для кейса КРОК. Превращаем поток логов диалогов
сотрудников с ИИ-агентами в понятную аналитику для CTO: классификация запросов → сценарии
(use-cases) → саммари → живой дашборд + ROI/FTE.

> Переносимый контекст агентов — `AGENTS.md`; актуальная карта реализации —
> `docs/CODEBASE_MAP.md`. Контекст кейса — в `docs/`. ТЗ бэкенда —
> `docs/backend/BACKEND_TASK.md`, ТЗ ML — `ml_service/ТЗ.md`, контракты — `docs/contracts/`.
> Локальные исторические решения/статусы могут быть в `docs/decisions/DECISIONS.md` и `TASKS.md`,
> но они исключены из Git и могут отставать от кода. Запуск стека: `make up`; demo-логин:
> `test@gmail.com` / `test123`.

## Цель продукта

- Ответить руководителю на вопрос «что происходит с ИИ в компании и что делать дальше».
- Must-have: классификация, кластеризация в сценарии, саммари сценариев, дашборд.
- Киллер-фича: ROI/FTE — оцифровка пользы ИИ в часах и рублях (боль заказчика).
- Приоритет MVP: воспроизводимый пайплайн + понятный дашборд + demo-данные.

## Архитектура (инварианты)

- Плоская монорепа: `backend/` (API + оркестрация + БД + ROI + auth), `ml_service/` (ML-пайплайн),
  `frontend/` (дашборд). Общие контракты — `docs/contracts/`.
- **Backend — модульный монолит** (FastAPI, паттерн из `template/backend`): `api/` (тонкие
  роутеры) → `service/` (бизнес-логика) → `domain/` (схемы/enum) → `database/` (SQLAlchemy async
  + Alembic). Не плодим новые сервисы без веской причины.
- **Модель интеграции — стриминговый CQRS** (см. `docs/decisions/DECISIONS.md` → D1):
  - write: backend шлёт батчи логов в ML `PUT /api/v1/logs` (async);
  - recompute: `POST /api/v1/recompute` — тяжёлый пересчёт кластеров + LLM-нейминг (вручную/по крону);
  - read: `GET /api/v1/statistics` — мгновенно из стора ML, без вызова моделей.
- **ML владеет аналитическим стором** (Qdrant + лёгкая мета-БД, D2). **Backend владеет
  бизнес-состоянием** (пользователи, ingestion-источники, сырые ROI-поля) и **считает ROI** (D6).
- Backend НЕ импортирует код `ml_service` и наоборот — только через контракты. Дашборд —
  глобальный живой с фильтрами `source_id/from/to` (D3).

## Границы ответственности

- Backend: ingestion датасета (+ live-webhook `POST /api/v1/logs` c `X-Ingest-Token`, D7), нормализация
  → записи `log.schema.json`, стриминг в ML, триггер recompute, хранение бизнес-состояния, ROI,
  read-API для дашборда, auth.
- ML: приём логов, классификация, эмбеддинги, онлайн-кластеризация, пересчёт (UMAP+HDBSCAN),
  саммаризация, агрегаты для `/statistics`. Подробности — `ml_service/ТЗ.md`.
- Frontend: дашборд для CTO. Каждый график отвечает на управленческий вопрос.

## Рабочие правила

- Перед новым кодом ищи существующий паттерн (в `backend/` или в `template/backend/`).
- Для сложных изменений — сначала короткий план, потом реализация минимальными патчами.
- Меняй существующие файлы вместо новых абстракций. Патчи маленькие и ревьюабельные.
- После значимых правок запускай минимальную релевантную проверку (lint / unit).
- Любой новый endpoint объявляет свою Pydantic-схему ответа. Контракты — в `docs/contracts/`.
- `template/` — ТОЛЬКО референс прошлого проекта. Не запускаем и не правим его; переносим паттерны
  в `backend/` осознанно, а не копируем доменную логику dating.

## Quality gates

- Backend: `ruff` + unit-тесты проходят. Новый endpoint — со схемой и примером в контракте.
- Изменение `/statistics` → меняется `schema_version`. Изменение таксономии → `taxonomy_version`.
- Демо должно подниматься одной командой (`make up` / `make demo`).

## Безопасность

- Никогда не читай и не печатай секреты из `.env`, `*/secrets/**`, ключей.
- `OPENROUTER_API_KEY` и `ML_SERVICE_TOKEN` — только через env, не в Git.
- Не переписывай большие датасеты in-place без подтверждения.
