# Prompt Radar — шпаргалка для защиты (ML)

Составлено 2026-07-26 по коду `ml_service/` в рабочем дереве. Все числа взяты из кода и
артефактов модели, а не из планов. Парная шпаргалка по backend и интеграции —
[`docs/backend/DEFENSE_BRIEF.md`](../docs/backend/DEFENSE_BRIEF.md).

> **Главный нарратив ML-части:** мы не просто «прогнали кластеризацию». Мы построили пайплайн,
> который **никогда не выдаёт догадку за факт**: низкая уверенность → `unknown`, нет сигналов о
> сбоях → `status: not_available`, нет модели → явный fallback с пометкой в `pipeline_metadata`,
> нет LLM → технические имена вместо выдуманных. Это и есть то, что отличает инженерию от демо.

---

## 1. Роль ML в продукте — 60 секунд

Backend отдаёт поток нормализованных логов. ML отвечает на три вопроса и **владеет аналитическим
состоянием**:

1. **Что это за задача?** → CatBoost по эмбеддингу запроса, таксономия v1 (7 классов).
2. **Какую работу человек реально делает?** → кластеризация запросов в сценарии: онлайн по cosine,
   тяжёлый пересчёт UMAP + HDBSCAN.
3. **Что внутри сценария?** → LLM-саммари со структурированным выходом: имя ≤ 4 слов, цель
   пользователя, боли, потенциал автоматизации.

Плюс отдаёт готовую read-модель `/statistics`, чтобы дашборд не ждал модели.

**ROI считает backend, не ML** (решение D6). ML отдаёт только назначения
`request_id → task_type, scenario_id`. Это осознанная граница: ROI зависит от корпоративных
ставок, а не от векторов, и раздувать ML-контракт бизнес-полями мы не стали.

## 2. Архитектура ML-контура

```text
        backend  ──PUT /api/v1/logs (батчи ≤200, X-Service-Token)──►  ml-service :8000
                                                                            │
                                          202 Accepted сразу               │ фон
                                                                            ▼
                                                              IngestQueue (asyncio)
                                                                            │ concurrency=8
                                                                            ▼
                              ┌──────────────── _process_one(log) ────────────────┐
                              │ 1. dedup по request_id (meta.has_assignment)      │
                              │ 2. preprocess + long-text стратегия               │
                              │ 3. ОДИН эмбеддинг (Ollama / OpenRouter)           │
                              │ 4. CatBoost по этому же вектору → task_type       │
                              │ 5. online cosine assign внутри task_type          │
                              │ 6. failure-сигналы из полей лога                  │
                              │ 7. запись: meta.db (assignment) + Qdrant (вектор)  │
                              └────────────────────────────────────────────────────┘
                                            │                        │
                                            ▼                        ▼
                                  meta.db (SQLite)             Qdrant :6333
                            assignments / clusters /          векторы + payload
                            recompute_jobs / ingest_log

        backend  ──POST /recompute──►  UMAP+HDBSCAN по каждому task_type
                                       → стабилизация scenario_id по центроидам
                                       → репрезентативные примеры → LLM-саммари
                                       → перезапись meta + Qdrant

        backend  ──GET /statistics /scenarios /assignments──►  чтение из стора,
                                                               БЕЗ вызова моделей
```

### Почему CQRS, а не «один эндпоинт, который всё считает»

Три потока разведены сознательно (решение D1):

| Поток | Стоимость | Свойство |
|---|---|---|
| **write** `PUT /logs` | эмбеддинг + CatBoost на запись | отвечает `202` мгновенно, работа в фоне |
| **recompute** `POST /recompute` | UMAP + HDBSCAN + LLM по всем данным | тяжёлый, запускается вручную |
| **read** `GET /statistics` | только SQL + агрегация в памяти | никогда не вызывает модели |

Что это даёт на защите: **дашборд не может «подвиснуть на модели»**, а самая дорогая и самая
рискованная операция (LLM-нейминг) не находится на пути пользовательского запроса. Ручной триггер
recompute — главный де-риск демо: мы не зависим от того, ответит ли провайдер в момент показа.

## 4. API ML

Префикс `/api/v1`, все вызовы требуют `X-Service-Token`. Health — без префикса.

| Метод | Путь | Семантика |
|---|---|---|
| PUT | `/logs` | приём батча, `202`, идемпотентно по `request_id`, ответ `{accepted, duplicates, rejected, source_id}` |
| POST | `/recompute` | `202` + `job_id`, работа в `BackgroundTasks` |
| GET | `/recompute/{job_id}` | `pending \| running \| completed \| failed` + `clusters_created`, `scenarios_named` |
| GET | `/statistics` | read-модель по `statistics.schema.json`, фильтры `source_id/from/to` |
| GET | `/scenarios`, `/scenarios/{id}` | сценарии с саммари |
| GET | `/assignments` | `request_id → task_type, scenario_id, ...`, пагинация — для ROI-джойна backend |

**Тонкость контракта, которую надо знать:** у `LogBatch` **нет** верхнеуровневого `source_id` —

лог батча. Если этого не делать, ломается атрибуция источника и фильтры дашборда.

## 5. Путь одной записи (write path)

`app/main.py:_process_one`. Порядок важен, и на защите его стоит проговорить именно так:

1. **Отклонение пустых.** Пустой `query_text` → `rejected`, батч не падает.
2. **Дедуп.** `meta.has_assignment(request_id)` → `duplicate`. Плюс дедуп внутри батча через
   `seen_in_batch`. Идемпотентность — свойство контракта, а не случайность.
3. **Валидация времени.** Некорректный `timestamp` → `rejected` (иначе поедут тренды и динамика).
4. **Preprocess.** Нормализация пробелов; технические токены **не** вычищаются — они несут смысл
   в корпоративных запросах.
5. **Long-text стратегия.** ≤ 8000 «токенов» (слов) → `direct`. Длиннее → перекрывающиеся окна
   512 слов с overlap 64, затем компактное представление: первые N чанков + **последний**
   (в конце запроса обычно лежит собственно инструкция). Стратегия и число чанков пишутся в
   метрики — молчаливого обрезания документа нет.
6. **Один эмбеддинг на запись.** Тот же вектор идёт и в CatBoost, и в кластеризацию, и в Qdrant.
   Это не микро-оптимизация, а гарантия согласованности: классификация и кластеризация живут в
   одном пространстве.
7. **Классификация** (см. §6).
8. **Онлайн-назначение** в кластер внутри своего `task_type` (см. §8).
9. **Failure-сигналы** из полей лога: `response_status ∈ {error, failed, failure, timeout}`,
   `error_code`, `user_feedback < 0`, `retry_count > 0`. Ничего не додумывается.
10. **Запись**: `meta.upsert_assignment` (SQLite) + `qdrant.upsert` (вектор + payload).

Параллелизм: `IngestQueue` (asyncio) + `IngestWorker` с `concurrency=8` и семафором.
Исключение на одной записи логируется и не роняет ни батч, ни воркер.

## 6. Классификация — самая частая тема вопросов

### Что именно сделано

**CatBoost по эмбеддингу запроса**, а не по «мешку слов»: текст → вектор (2560) → PCA (256) →
CatBoost MultiClass → 7 классов. Артефакт `app/models/catboost_task_classifier.cbm`,
рядом `.pca.npz` (mean + components) и `.meta.json` с описанием входа.

### Почему CatBoost, а не fine-tune трансформера или zero-shot LLM

Три причины, все проверяемые:

1. **Стоимость инференса.** Классификация идёт на каждую запись потока. CatBoost по готовому
   вектору — микросекунды CPU. LLM-классификация 4860 записей — это деньги и минуты, причём на
   каждый повторный прогон.
2. **Вектор всё равно нужен** для кластеризации. Раз эмбеддинг уже посчитан, классификатор
   поверх него практически бесплатен — мы переиспользуем самый дорогой артефакт.
3. **Детерминированность и калибровка.** У CatBoost есть `predict_proba`, то есть управляемый
   порог уверенности. У zero-shot LLM «уверенность» — это самоотчёт модели, на нём нельзя
   построить честный `unknown`.

LLM при этом не выброшен: он остаётся **fallback'ом** и делает то, что умеет лучше — нейминг и
саммари сценариев, где нужен язык, а не калибровка.

### Порог уверенности и `unknown` vs `other`

```
confidence < 0.30  →  task_type = "unknown"        (per-record: «мы не уверены»)
```

- **`unknown` — это неуверенность модели.** Пер-рекордное значение.
- **`other` — это продуктовый класс** «нерабочее / общие вопросы / аномалии», плюс агрегированный
  хвост в Top-N распределении.
- **Их запрещено смешивать.** В `top_n_distribution` ключ `unknown` помечен `protected_keys` и
  **никогда** не сливается в `other`. Это прямо закодировано и покрыто тестами.

Почему это важно на защите: если смешать, дашборд начнёт врать в обе стороны — «Другое» будет
выглядеть как реальный класс задач, а честное «не уверены» исчезнет из виду.

**Почему порог 0.30, а не 0.5.** Замеряли: при 0.45 около половины реального трафика уезжало в
`unknown` — дашборд становился бесполезным при формально «аккуратной» модели. 0.30 — рабочий
баланс между «не врать» и «показать картину». Порог живёт в конфиге и попадает в
`pipeline_metadata.classifier_confidence_threshold`, то есть он аудируемый, а не спрятанный.

### Каскад деградации классификатора

`fallback_mode` в конфиге, в Compose — `fail_fast`:

| Режим | Поведение | Когда уместен |
|---|---|---|
| `fail_fast` | нет модели → `CLASSIFIER_NOT_AVAILABLE`, readiness `degraded` | **прод/демо**: лучше явная ошибка, чем тихий мусор |
| `llm` | классификация LLM по описаниям классов из таксономии, structured output | нет `.cbm`, но есть провайдер |
| `embedding_centroid` | ближайший центроид класса по cosine | есть векторы, нет модели |
| `keyword` | эвристика по ключевым словам | **только тесты**, в проде запрещено |

Отдельно зафиксировано в коде: **фиктивное обучение CatBoost на микро-датасете запрещено**.
Если артефакта нет — мы деградируем открыто, а не «обучаем модель на десяти примерах».

## 7. Обучение модели — здесь надо быть готовым к жёстким вопросам

`catboost/train_catboost.py`. Фактические параметры из артефакта и кода:

| Параметр | Значение |
|---|---|
| Датасет | 4858 записей (сгенерированный, `category` как эталон) |
| Эмбеддинги | OpenRouter `qwen/qwen3-embedding-4b`, **dim 2560** |
| Понижение размерности | PCA 2560 → **256** |
| Разбиение | `train_test_split(test_size=0.2, stratify=y, random_state=seed)` |
| CatBoost | `iterations=500`, `lr=0.05`, `depth=6`, `loss=MultiClass`, `eval_metric=TotalF1:average=Macro` |
| Регуляризация | `l2_leaf_reg=5`, `min_data_in_leaf=5`, `random_strength=1` |
| Дисбаланс | `auto_class_weights="Balanced"` |
| Ранняя остановка | `early_stopping_rounds=150`, `use_best_model=True` |
| **Holdout accuracy** | **0.8097 (80.97%)** |
| Отчётность | `classification_report` (precision/recall/F1 по классам) + confusion matrix |

Кэш эмбеддингов — `catboost/embeddings_cache.npz` с fingerprint по текстам: повторное обучение не
пересчитывает векторы и не тратит кредиты.

### Два методологических изъяна — назвать самому, до того как спросят

Это самый вероятный источник неудобных вопросов. Оба — реальные, оба имеют честный ответ.

**1. PCA обучается на полном наборе до сплита.**
В коде: `pca.fit_transform(X)` для всех данных, и только потом `train_test_split`. Значит базис PCA
видел признаки holdout'а.
→ *Как отвечать:* «PCA здесь **без учителя** — он никогда не видит `y`, поэтому утечки метки нет.
Утечка ограничена тем, что базис знает о распределении признаков holdout'а; на 4858 записях и 256
компонентах эффект малый, но признаю: это не чистая out-of-sample оценка. Правильно — обучать PCA
только на train и применять к test; это одна строка, и в следующей итерации мы её сделаем.»

**2. Holdout используется для early stopping — то есть это validation, а не test.**
В коде: `eval_set=test_pool` + `use_best_model=True` + `early_stopping_rounds=150`. Модель
выбирается по тому же набору, на котором мы потом сообщаем accuracy.
→ *Как отвечать:* «Согласен, `0.8097` — оптимистичная оценка, потому что holdout участвовал в
выборе итерации. Честно это называется validation accuracy. Нужен трёхчастный сплит
train/val/test: early stopping по val, финальная цифра по test. Порядок ожидаемой просадки —
единицы процентов, потому что выбирается только число итераций, а не гиперпараметры.»

**Почему такой ответ сильнее, чем защита цифры:** жюри проверяет, понимаешь ли ты, что измерил.
Инженер, который сам называет ограничение своей метрики и знает точный фикс, выглядит сильнее
того, кто настаивает на «80% — значит хорошо».

### Третий момент: природа данных

Датасет **синтетический, сгенерирован LLM**, и `category` в нём — метка того же генератора.
Значит классификатор учится воспроизводить **политику разметки генератора**, а не объективное
намерение человека.
→ *Как отвечать:* «На реальном корпоративном трафике цифра будет другой, и мы это знаем.
`gold_category` мы сохраняем в backend именно для того, чтобы на живых данных можно было
переоценить качество, а не чтобы использовать её в расчётах. Ни один продуктовый показатель
дашборда на `category` не опирается — только оценка классификатора.»

### Совместимость эмбеддингов обучения и рантайма — главный технический риск

Модель обучена на **2560-мерных** векторах `qwen3-embedding-4b` от OpenRouter. В рантайме
`ML_MODE=offline` берёт Ollama `qwen3-embedding:4b` — **то же семейство и та же размерность**.
Именно поэтому в конфиге сознательно выбраны «одинаковые семейства моделей в обоих режимах»: это
позволяет переключать offline/online без переобучения.

Что произойдёт при несовпадении: `_apply_pca` увидит другую размерность, залогирует предупреждение
и **пропустит PCA**, дальше CatBoost получит не 256 признаков и упадёт → сработает `fallback_mode`.
При `fail_fast` это явная ошибка, а не тихий мусор. Практический вывод: `mock`-эмбеддинги (384)
несовместимы с реальным классификатором **by design**, и это правильно.

## 8. Онлайн-кластеризация (write path)

`CosineClusterer`, порог **0.85**:

```
1) взять максимум cosine к центроидам ТОГО ЖЕ task_type
2) если ≥ 0.85 → назначить + обновить центроид бегущим средним:
      centroid = (centroid * n + vec) / (n + 1)
3) иначе → новый scenario_id = "{task_type}:cluster_{n}"
```

Два вопроса, которые обязательно зададут:

**«Почему кластеризуете внутри `task_type`, а не по всему пространству?»**
Потому что сценарий — это единица *работы*, а не тема. «Напиши письмо клиенту» и «объясни, почему
письмо не отправилось» семантически близки, но это разные задачи с разной ценой ручного
выполнения. Разделение по `task_type` не даёт им склеиться и даёт ROI осмысленные разрезы.

**«Почему 0.85?»** Это порог «тот же самый сценарий, другими словами». Ниже — начинают склеиваться
разные сценарии; выше — каждый перефраз плодит новый кластер. Порог в конфиге и в
`pipeline_metadata.online_similarity_threshold` — его видно и можно оспорить на данных.

**Честное ограничение:** центроиды живут **в памяти процесса** и не восстанавливаются из мета-стора
после рестарта (TODO в `cosine_clusterer.py`; методы `dump_centroids`/`load_centroids` уже
написаны, вызов на старте — нет). Следствие: после рестарта онлайн-нумерация кластеров начинается
заново. Путь стабилизации — heavy recompute, который перекладывает всё в согласованное состояние.
Так и говорить: «онлайн-слой — быстрое приближение, источник истины по сценариям — recompute».

## 9. Heavy recompute — UMAP + HDBSCAN

`app/recompute/job.py` + `clustering_batch/umap_hdbscan.py`. Прогон **по каждому `task_type`
отдельно**, CPU-heavy часть уходит в `asyncio.to_thread`, чтобы API продолжал отвечать на поллинг.

| Этап | Параметры |
|---|---|
| UMAP | `n_neighbors=15`, `n_components=10`, `min_dist=0.0`, `metric=cosine`, **`random_state=42`** |
| HDBSCAN | `min_cluster_size=10`, `min_samples=4`, `metric=euclidean`, `cluster_selection_method=eom` |
| Cap | не более **5** сценариев на `task_type`, остальные переназначаются к ближайшему центроиду |
| Стабилизация | сопоставление центроидов, порог cosine **0.75** |

### Почему UMAP перед HDBSCAN, а не HDBSCAN напрямую

HDBSCAN плохо работает в высокой размерности: плотности размываются (проклятие размерности), и
почти всё уезжает в шум. UMAP сохраняет локальную структуру и опускает 2560 → 10, где понятие
плотности снова осмысленно. `min_dist=0.0` — потому что нам нужны **компактные плотные группы**
для кластеризации, а не красивая картинка для человека. `metric=cosine` на входе — потому что
эмбеддинги сравниваются по направлению, а не по длине.

### Стабилизация `scenario_id` — то, чем стоит гордиться

Без неё каждый пересчёт перенумеровывал бы сценарии, и дашборд после recompute показывал бы
«новые» сценарии вместо тех же самых — тренды и ROI по сценариям стали бы мусором.

`stabilize_scenario_ids` делает жадное двудольное сопоставление: считает cosine между новыми и
старыми центроидами того же `task_type`, сортирует пары по убыванию похожести, назначает лучшие
непересекающиеся пары при similarity ≥ 0.75, а несопоставленным выдаёт свободные индексы, не
конфликтующие с переиспользованными. То есть **`scenario_id` — это идентичность сценария во
времени**, а не порядковый номер прогона.

### Выбор репрезентативных примеров

`select_representatives`: KNN ближайших к центроиду + **несколько граничных (самых далёких)**
образцов, с дедупом по точному тексту, 10 примеров по умолчанию. Граничные нужны, чтобы LLM
увидел края кластера и не назвал сценарий по его самому типичному представителю. Если Qdrant
доступен — примеры берутся KNN-поиском по стору, иначе по членам кластера в памяти.

### Fallback'и кластеризации — все помечены

| Ситуация | Поведение | `statistical_reliability` |
|---|---|---|
| `n = 0` | пустой результат | `low`, `fallback_used=empty` |
| `n < min_cluster_size` | один центроид на группу | `low`, `small_group_centroid` |
| нет umap/hdbscan в окружении | один центроид, ошибка в лог | `low`, `libs_unavailable` |
| HDBSCAN отправил всё в шум | схлопывание в один кластер | `low`, `all_outliers_collapsed` |
| нормальный путь | UMAP+HDBSCAN | `high`, `fallback_used=none` |

Значение `statistical_reliability` доезжает до дашборда по сценарию. То есть **пользователь видит,
когда выводу можно верить меньше** — это ровно та честность, которую мы защищаем.

**HDBSCAN outlier (`-1`) ≠ ошибка агента.** Это запрос, не похожий ни на один устойчивый сценарий:
редкая или новая задача. Про сбои говорит только `failure_analysis`. Путать эти две сущности —
типичная ошибка, и на дашборде они разведены.

**Ограничение:** пересчёт полный, не инкрементальный — `_pending_for_recompute()` поднимает все
назначения и все векторы. На демо-объёмах это правильный компромисс (проще и воспроизводимее),
на больших данных потребуется инкрементальность.

## 10. Саммаризация сценариев

`app/pipeline/summarization.py`. Не «попросили LLM написать текст», а контракт:

- **Structured output**: `chat.with_structured_output(ScenarioSummary)` через LangChain.
- **Pydantic-валидация** с жёсткими правилами: `name` непустое и обрезается до **4 слов**
  валидатором; `automation_potential` приводится к `low|medium|high`, любое другое значение → `low`.
- **Ретраи**: до 2 повторов (`max_llm_retries`), затем **технический fallback**
  `Сценарий {task_type} {n}` с `summary="Summary unavailable"`.
- В промпте прямая инструкция «не выдумывай факты» и «по-русски, если примеры на русском».

Почему это важно проговорить: fallback возвращает **честно бесполезное** имя вместо
галлюцинированного осмысленного. Пустой дашборд лучше неверного — это и есть инженерное решение,
а не недоработка.

`name ≤ 4 слов` — не каприз: имя сценария живёт в легендах графиков и таблицах ROI, где длинная
строка ломает читаемость.

## 11. Read-модель `/statistics`

`app/pipeline/aggregation/builder.py`. Чистые функции, покрытые юнит-тестами, без обращения к
моделям. `schema_version = 2.0.0`, `pipeline_version = 0.3.0-mvp`, `taxonomy_version = v1`.

Что внутри и почему именно так:

- **`tasks_distribution`** — Top-7 + `other` для хвоста, при этом `unknown` защищён от слияния.
- **`top_scenarios`** — Top-9 + бакет `other`, у которого **`summary = None`**: у агрегата нет
  и не может быть осмысленного саммари, поэтому мы его не подделываем.
- **`dynamics`** — счётчики по дням из `timestamp`.
- **Тренды** — сравнение половин периода (`up | down | stable | new | insufficient_data`).
  Защита от артефактов холодного старта: рост считается только при `total ≥ 20` и
  `previous ≥ 5`, порог ±15%; при `previous == 0` → `new` **без процента** (иначе получались бы
  «+4600%»). Это прямой ответ на вопрос «почему у вас нет процентов у новых сценариев».
- **`failure_analysis`** — доступен **только если в данных есть каналы качества**. Если ни одна
  запись не несёт `response_status` / `error_code` / `user_feedback` / `retry_count`, отдаём
  `{"status": "not_available"}` вместо нулей. Ноль означал бы «сбоев нет» — это была бы ложь.
- **`freshness`** — `last_recompute_at`, `logs_since_last_recompute`, `recompute_pending`:
  дашборд честно показывает, что данные ушли вперёд от последнего пересчёта.
- **`pipeline_metadata`** — всё, что влияет на результат: провайдеры и модели эмбеддингов/LLM,
  режимы, порог классификатора, порог онлайн-кластеризации, параметры UMAP/HDBSCAN, версия
  таксономии.

Про `pipeline_metadata` стоит сказать отдельно: **любую цифру дашборда можно воспроизвести, потому
что рядом с ней лежат все параметры, которыми она получена.** Это то, что превращает демо в
инженерный артефакт.

## 12. Сторы и деградация

### Qdrant + мета-БД

- **Qdrant** — векторы и payload (`request_id`, `task_type`, `scenario_id`, `source_id`,
  `timestamp`, флаги). Коллекция создаётся при старте. Batch upsert по 64 точки.
- **meta.db (SQLite)** — `assignments`, `clusters` (включая центроиды), `recompute_jobs`,
  `ingest_log`. Лёгкая, персистентная, живёт в volume `ml_meta_data`.

Разделение простое: Qdrant отвечает на «кто похож», SQLite — на «что мы уже решили».

**In-memory fallback Qdrant** управляется двумя флагами: `ALLOW_INMEMORY_STORE` (разрешить mock) и
`QDRANT_REQUIRED` (запретить mock). В Compose стоит `ALLOW_INMEMORY_STORE=false` +
`QDRANT_REQUIRED=true` — то есть **на демо подмена стора невозможна**, сервис откажется стартовать
без реального Qdrant. В юнит-тестах наоборот. Это ровно тот случай, когда «удобный fallback»
намеренно выключен там, где он мог бы соврать.

### `/health/ready` — честная деградация

Возвращает `ready | degraded | not_ready` и разложенные проверки: `config`, `embeddings_mode`,
`embeddings_provider`, `llm_provider:status`, `classifier`, `qdrant`, `meta_store`,
`clusters_loaded`.

Логика: невалидный конфиг или отсутствующий meta-store → `not_ready`; классификатор на fallback'е,
Qdrant в mock-режиме или LLM без ключа → `degraded`. Backend отражает это в своём `/api/ready`,
причём `degraded` **не блокирует** готовность приложения — дашборд продолжает отдавать последний
валидный снапшот.

### Коды ошибок

`INVALID_REQUEST · INGEST_VALIDATION_FAILED · CLASSIFIER_NOT_AVAILABLE ·
EMBEDDING_PROVIDER_UNAVAILABLE · EMBEDDING_REQUEST_FAILED · LLM_PROVIDER_UNAVAILABLE ·
LLM_RESPONSE_INVALID · CLUSTERING_FAILED · STORE_UNAVAILABLE · RECOMPUTE_FAILED · INTERNAL_ERROR`

Формат `{code, message, retryable, details?}`. Секреты и stack trace наружу не уходят.

### Эмбеддинги: устойчивость провайдера

`HttpEmbeddingAdapter` — батчи (32), retry, **adaptive concurrency**: при ответах «busy/429» лимит
параллелизма снижается, при успехах растёт. Плюс кэш `text → vector` по хешу. Размерность берётся
из ответа провайдера, а не хардкодится. Это про то, что мы готовы к rate limit'ам реального
провайдера, а не только к идеальному локальному прогону.

## 13. Воспроизводимость

- `random_state=42` у UMAP; `random_seed` у CatBoost; `stratify` в сплите.
- Все параметры, влияющие на результат, — в `config.yaml` и в `pipeline_metadata` ответа.
- Кэш эмбеддингов с fingerprint по текстам → повторное обучение детерминировано и бесплатно.
- Детерминированная загрузка сид-датасета в backend + снапшот после `recompute` дают
  повторяемую картину дашборда.

Оговорка, которую честнее сказать самому: UMAP с фиксированным `random_state` работает
однопоточно и всё равно может давать микроразличия между версиями библиотек/платформами — поэтому
воспроизводимость мы обеспечиваем на уровне «тот же образ + тот же конфиг», а не «побитово везде».

## 14. Ожидаемые вопросы и короткие ответы

**«Почему 7 классов, а не 20?»**
Таксономия v1 отвечает на управленческий вопрос, а не описывает мир. 7 классов различимы на глаз,
устойчиво размечаются и покрывают трафик; версия зафиксирована (`taxonomy_version`), расширение —
согласованное изменение контракта с backend и frontend, а не правка на месте.

**«80% accuracy — это мало.»**
Во-первых, это 7 классов при `Balanced` веcах — baseline случайного угадывания ~14%. Во-вторых,
цифра снята на синтетике, где метка — политика генератора, и на реальном трафике она будет иной;
именно поэтому у нас есть порог уверенности и `unknown`, а не слепое доверие модели. В-третьих,
эта цифра — validation, а не test (см. §7), и я знаю, как её измерить честно.

**«Как понять, что кластеры осмысленные, а не случайные?»**
Три проверяемых признака: `statistical_reliability` от HDBSCAN по каждому сценарию; доля outliers
на дашборде; и репрезентативные примеры в карточке сценария — их можно прочитать глазами и
сопоставить с именем. Плюс `scenario_id` стабилен между пересчётами, то есть кластеры
воспроизводятся, а не пересобираются каждый раз заново.

**«Что если LLM недоступен?»**
Классификация не страдает — это CatBoost. Пострадает только нейминг: сценарии получат технические
имена, `automation_potential=low`, и это видно в `pipeline_metadata`. Дашборд остаётся рабочим.

**«Почему кластеризация не в реальном времени, а по кнопке?»**
Она в реальном времени — онлайн-назначение по cosine работает на каждую запись. По кнопке
запускается *пересчёт структуры* (UMAP+HDBSCAN + нейминг): это глобальная операция по всем данным,
её нельзя делать на каждый лог, и она тратит кредиты LLM. Разделение online/heavy — это D1.

**«Утечки данных в обучении есть?»**
Да, две, обе называю сам: PCA обучен на полном наборе, и holdout использован для early stopping.
Метки утечки нет, оценка слегка оптимистична, фикс — трёхчастный сплит и PCA только на train.

**«Как масштабируется?»**
Read-путь — SQL + агрегация, масштабируется тривиально. Write-путь — очередь в процессе с
concurrency 8; узкое место не CPU, а провайдер эмбеддингов, поэтому там adaptive concurrency и
кэш. Следующий шаг — внешний брокер и инкрементальный recompute вместо полного.

**«Почему SQLite, а не Postgres в ML?»**
Мета-БД ML держит десятки тысяч строк и одного писателя — процесс сервиса. SQLite покрывает это
без отдельного сервиса, а бизнес-состояние и без того живёт в Postgres на стороне backend
(решение D2). Если ML пойдёт в несколько реплик, мета-стор переезжает — интерфейс `MetaStore`
это позволяет.

## 15. Осознанные ограничения

| Ограничение | Почему так / что дальше |
|---|---|
| Онлайн-центроиды не восстанавливаются из мета-стора после рестарта | `dump_centroids`/`load_centroids` написаны, вызов на старте — TODO. Стабилизацию обеспечивает recompute |
| Recompute полный, не инкрементальный | Проще и воспроизводимее на демо-объёмах; инкрементальность — следующий шаг |
| Отсутствующий вектор в recompute заменяется нулевым | Дешёвая защита от падения, но нулевые векторы склеиваются в вырожденную группу. Правильно — исключать такие записи из прогона |
| Очередь и job-store — в памяти процесса | Одна реплика ML. Несколько потребуют внешнего брокера и общего job-store |
| PCA на полном наборе + holdout как val | См. §7, фикс известен |
| Датасет синтетический | `gold_category` сохраняется для переоценки на реальном трафике |
| `mock`-эмбеддинги несовместимы с обученной моделью | By design: 384 ≠ 2560, и при `fail_fast` это явная ошибка вместо тихого мусора |
