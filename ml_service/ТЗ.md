# Техническое задание

## ML-сервис аналитики пользовательских запросов к ИИ-агентам «Промпт-радар»

**Версия:** 1.1  
**Статус:** согласовано к началу разработки  
**Контур:** hackathon MVP  
**Расположение в monorepo:** `ml_service/`

---

## 1. Назначение документа

Документ определяет требования к ML-сервису проекта «Промпт-радар».

ML-сервис должен принимать подготовленный набор логов пользовательских запросов к корпоративным ИИ-агентам, выполнять классификацию запросов, находить устойчивые сценарии использования, формировать понятные описания сценариев и рассчитывать данные для аналитического дашборда.

Документ описывает:

- границы ответственности ML-сервиса;
- внутреннюю структуру сервиса;
- входные и выходные контракты;
- этапы ML-пайплайна;
- правила обработки длинных запросов;
- правила кластеризации, саммаризации и агрегации;
- управление состоянием анализа;
- требования к воспроизводимости, тестированию и Docker-развёртыванию.

## 2. Место ML-сервиса в общей архитектуре

Система разрабатывается в формате monorepo.

Основные компоненты:

```text
apps/web        Frontend и дашборд
apps/api        Main Backend, бизнес-логика и оркестрация
services/ml     ML-пайплайн аналитики запросов
contracts       Общие схемы интеграции
data            Примеры и подготовленные наборы данных
eval            Evaluation-наборы и отчёты качества
infra           Docker и локальное окружение
```

Схема взаимодействия:

```text
Frontend
   |
   v
Main Backend
   |
   | POST /api/v1/analyze
   | GET  /api/v1/analyses/{analysis_run_id}
   v
ML service
   |
   v
Shared run storage: /data/runs/{analysis_run_id}/
```

### 2.1. Ответственность ML-сервиса

ML-сервис отвечает за:

- чтение нормализованного входного файла;
- валидацию входных записей;
- обработку длинных запросов;
- классификацию запросов по типам задач;
- построение эмбеддингов;
- кластеризацию запросов в сценарии использования;
- определение выбросов и нетипичных запросов;
- генерацию названий и описаний сценариев;
- расчёт аналитических агрегатов;
- формирование `result.json`;
- формирование технических и ML-метрик;
- ведение состояния конкретного запуска анализа;
- возврат статуса и ошибок Main Backend.

### 2.2. Что не относится к ML-сервису

ML-сервис не отвечает за:

- пользовательскую авторизацию;
- загрузку файлов через пользовательский интерфейс;
- постоянное хранение истории запусков;
- хранение бизнес-сущностей приложения;
- формирование frontend-страниц;
- управление пользователями;
- создание дашборда;
- прямое взаимодействие с Frontend;
- принятие продуктовых решений на основании аналитики;
- доказательство факта, что ИИ-агент дал неправильный ответ, если во входных данных нет ответа агента, ошибки, обратной связи или других сигналов качества.

### 2.3. Основной принцип интеграции

Большие массивы логов не передаются в теле HTTP-запроса.

Main Backend:

1. создаёт `analysis_run_id`;
2. нормализует и валидирует исходный датасет;
3. записывает данные в `/data/runs/{analysis_run_id}/input.jsonl`;
4. вызывает ML-сервис и передаёт `input_uri`;
5. периодически запрашивает статус;
6. после завершения получает `result_uri`;
7. валидирует `result.json` по общей схеме;
8. сохраняет необходимые данные и отдаёт их Frontend.

ML-сервис:

1. получает `analysis_run_id` и `input_uri`;
2. запускает обработку;
3. обновляет внутренний статус;
4. атомарно записывает итоговый результат;
5. возвращает путь к результату через status endpoint.

### 3.1. Архитектурные ограничения

- FastAPI-роутеры должны оставаться тонкими.
- Основная логика должна находиться в `pipeline`, `domain`, `runs` и `adapters`.
- Production-логика не должна существовать только в notebook.
- Поставщики LLM и embeddings должны подключаться через адаптеры.
- ML-сервис не должен импортировать код из `apps/api`.
- Общие контракты должны находиться в `contracts`.
- Замена модели или провайдера не должна требовать переписывания API.
- В рамках MVP не добавляются Kafka, Celery, Kubernetes и отдельный message broker.
- Асинхронность MVP может быть реализована через background task или внутренний worker процесса. Ограничение такого решения должно быть указано в README.

## 4. Конфигурация

Основные параметры хранятся в `services/ml/config.yaml`.

Секреты, API-ключи и provider URL, зависящие от окружения, должны переопределяться через environment variables.

Пример:

```yaml
server:
  host: "0.0.0.0"
  port: 8000

storage:
  runs_root: "/data/runs"

models:
  embeddings:
    provider: "ollama"

    ollama:
      model_name: "qwen3-embedding:4b"
      url: "http://ollama:11434/api/embed"

    openrouter:
      model_name: "qwen/qwen3-embedding-4b"
      url: "https://openrouter.ai/api/v1/embeddings"

  llm:
    provider: "openrouter"

    openrouter:
      model_name: "google/gemma-4-26b-a4b-it"
      url: "https://openrouter.ai/api/v1/chat/completions"

  classifier:
    provider: "catboost"
    model_path: "/app/models/catboost_task_classifier.cbm"
    confidence_threshold: 0.60
    fallback_mode: "llm"
    taxonomy_version: "v1"

long_text:
  strategy: "hierarchical"
  max_direct_tokens: 8192
  chunk_size_tokens: 6000
  chunk_overlap_tokens: 300
  preserve_head_tokens: 1000
  preserve_tail_tokens: 2000
  max_chunks: 32

clustering:
  scope: "within_task_type"

  umap:
    n_neighbors: 15
    n_components: 10
    min_dist: 0.0
    metric: "cosine"
    random_state: 42

  hdbscan:
    min_cluster_size: 5
    min_samples: 3
    metric: "euclidean"
    cluster_selection_method: "eom"

summarization:
  representative_examples_count: 10
  scenario_name_max_words: 4
  max_llm_retries: 2

aggregation_defaults:
  top_tasks_limit: 7
  top_scenarios_limit: 9
  trend_threshold_percent: 10.0
  trend_min_records_per_period: 5
```

### 4.1. Environment variables

Минимальный список:

```text
ML_CONFIG_PATH
ML_RUNS_ROOT
OLLAMA_URL
OPENROUTER_API_KEY
OPENROUTER_EMBEDDINGS_URL
OPENROUTER_CHAT_URL
CLASSIFIER_MODEL_PATH
LOG_LEVEL
```

### 4.2. Требования к конфигурации

- При запуске конфигурация должна проходить валидацию.
- Неизвестные обязательные параметры должны приводить к состоянию `not_ready`.
- API-ключи не должны храниться в Git.
- Названия моделей должны задаваться отдельно для каждого провайдера.
- `localhost` не должен быть зашит в production-конфигурацию контейнера.
- Все параметры, влияющие на результат анализа, должны попадать в метаданные запуска.

## 5. Входные данные

### 5.1. Формат

Входной файл имеет формат JSON Lines:

```text
/data/runs/{analysis_run_id}/input.jsonl
```

Каждая строка является самостоятельным JSON-объектом.

Минимальная запись:

```json
{
  "request_id": "req_101",
  "query_text": "Выгрузи отчёт из CRM",
  "timestamp": "2026-07-24T10:00:00Z"
}
```

Расширенная запись:

```json
{
  "request_id": "req_101",
  "query_text": "Выгрузи отчёт из CRM",
  "timestamp": "2026-07-24T10:00:00Z",
  "agent_id": "sales_assistant",
  "user_id": "user_42",
  "department": "sales",
  "response_text": "Готово, отчёт сформирован",
  "response_status": "success",
  "error_code": null,
  "response_latency_ms": 4200,
  "user_feedback": 1,
  "retry_count": 0,
  "metadata": {}
}
```

### 5.2. Обязательные поля

| Поле | Тип | Обязательное | Описание |
|---|---|---:|---|
| `request_id` | string | да | Уникальный идентификатор запроса |
| `query_text` | string | да | Текст пользовательского запроса |
| `timestamp` | ISO 8601 datetime | да | Время запроса |

### 5.3. Опциональные поля

| Поле | Назначение |
|---|---|
| `agent_id` | анализ по конкретному агенту |
| `user_id` | расчёт пользовательских срезов при разрешённой политике данных |
| `department` | бизнес-срезы |
| `response_text` | анализ ответа агента |
| `response_status` | сигнал успешности или ошибки |
| `error_code` | технический сигнал сбоя |
| `response_latency_ms` | сигнал производительности |
| `user_feedback` | пользовательская оценка |
| `retry_count` | число повторных попыток |
| `metadata` | дополнительные неструктурированные поля |

### 5.4. Правила валидации

- `request_id` не должен быть пустым.
- `query_text` не должен быть пустым после trim.
- `timestamp` должен быть корректным ISO 8601 datetime.
- Повторяющиеся `request_id` должны фиксироваться в метриках.
- Некорректные строки не должны останавливать весь batch, если доля ошибок не превысила допустимый предел.
- Для каждой отклонённой записи должна сохраняться причина.
- Порог допустимых ошибок должен быть настраиваемым.

Пример результата валидации:

```json
{
  "records_total": 1000,
  "records_valid": 992,
  "records_rejected": 8,
  "duplicate_request_ids": 2
}
```

## 6.3. Запуск анализа

### `POST /api/v1/analyze`

Request:

```json
{
  "analysis_run_id": "run_123",
  "input_uri": "/data/runs/run_123/input.jsonl",
  "output_uri": "/data/runs/run_123/result.json",
  "pipeline_config": {
    "taxonomy_version": "v1",
    "top_tasks_limit": 7,
    "top_scenarios_limit": 9,
    "generate_summaries": true,
    "detect_outliers": true,
    "analyze_failure_signals": true
  }
}
```

Response:

```http
202 Accepted
```

```json
{
  "analysis_run_id": "run_123",
  "status": "queued",
  "message": "Analysis accepted"
}
```

### Правила

- `analysis_run_id` должен быть уникальным.
- Повторный запрос с тем же `analysis_run_id` не должен запускать второй параллельный анализ.
- Если запуск уже выполняется, сервис возвращает его текущий статус.
- Если запуск завершён, сервис возвращает ссылку на существующий результат.
- Если предыдущий запуск завершился ошибкой, повторный запуск разрешён только при явном `force_restart: true` либо через отдельный endpoint, если он будет добавлен.
- `input_uri` должен находиться внутри разрешённого runs root.
- Произвольное чтение файлов вне `/data/runs` запрещено.

## 8.1. Предобработка

Предобработка должна:

- нормализовать пробелы;
- сохранять исходный текст без изменения;
- создавать отдельное нормализованное представление;
- не удалять значимые технические конструкции;
- фиксировать длину текста;
- оценивать число токенов;
- определять язык, если это необходимо для выбранной модели;
- выявлять пустые или технически некорректные записи;
- не изменять `request_id`.

Рекомендуемые поля внутренней записи:

```json
{
  "request_id": "req_101",
  "original_text": "Выгрузи отчёт из CRM",
  "normalized_text": "Выгрузи отчёт из CRM",
  "estimated_token_count": 6,
  "language": "ru"
}
```

---

## 8.2. Обработка длинных запросов

Запросы могут быть существенно длиннее контекстного окна embedding-модели. Сервис не должен молча обрезать текст.

### Стратегия MVP

Если текст не превышает `max_direct_tokens`, он обрабатывается напрямую.

Если текст превышает лимит:

1. текст разбивается на перекрывающиеся chunks;
2. сохраняется начало и конец запроса;
3. для каждого chunk извлекается краткое намерение и ключевые действия;
4. формируется сводное представление запроса;
5. классификация и embedding выполняются по сводному представлению;
6. в результат записывается информация об использованной стратегии.

Пример:

```json
{
  "request_id": "req_long_1",
  "original_token_count": 98500,
  "long_text_strategy": "hierarchical",
  "chunks_processed": 17,
  "text_was_truncated": false
}
```

### Обязательные требования

- Молчаливое обрезание запрещено.
- При достижении `max_chunks` сервис должен явно зафиксировать ограничение.
- Ошибка отдельного chunk не должна обязательно останавливать весь batch.
- Стратегия обработки должна быть воспроизводимой и отражаться в метриках.

## 8.3. Классификация задач

### Цель

Присвоить каждому запросу один верхнеуровневый `task_type`.

Пример таксономии v1:

```text
text_generation
information_search
data_analysis
code_help
explanation_learning
planning_task_management
communication
document_processing
automation_monitoring
other_business
non_work
unknown
```

Финальный список должен храниться в версионируемой таксономии:

```text
services/ml/app/domain/taxonomy.py
```

или в отдельном YAML/JSON-файле.

### Основной вариант

- `CatBoostClassifier`;
- заранее обученный и проверенный артефакт модели;
- модель загружается из `model_path`;
- результат содержит предсказанный класс и confidence.

Пример:

```json
{
  "task_type": "data_analysis",
  "classification_confidence": 0.91,
  "classification_model_version": "catboost-v1"
}
```

### Низкая уверенность

Если confidence ниже `confidence_threshold`:

```text
task_type = unknown
```

`unknown` означает, что классификатор не уверен в классе.

### Отличие `unknown` и `other`

- `unknown` используется на уровне отдельной записи при низкой уверенности классификатора.
- `other` используется только как агрегированный хвост на дашборде, когда категории или сценарии не вошли в Top N.

### Отсутствие модели

Запрещается автоматически обучать фиктивный CatBoost на микро-датасете только для того, чтобы API не падало.

Допустимые режимы:

1. `fail_fast`  
   Сервис не готов к анализу и сообщает `MODEL_NOT_AVAILABLE`.

2. `llm_fallback`  
   Используется LLM-классификация по фиксированной таксономии.

3. `embedding_centroid_fallback`  
   Используются заранее подготовленные центроиды классов.

Выбранный режим должен быть явно указан в конфигурации и метриках результата.

Пример:

```json
{
  "classifier_mode": "llm_fallback",
  "classifier_status": "degraded"
}
```

## 8.4. Построение эмбеддингов

### Требования

- Провайдер должен подключаться через общий интерфейс.
- Для Ollama и OpenRouter используются отдельные provider-specific model IDs.
- Должны быть настроены timeout и retry.
- Необходимо ограничить число параллельных запросов.
- Размер batch должен быть конфигурируемым.
- Ошибки должны классифицироваться как retryable или non-retryable.
- В метриках должны сохраняться provider, model name и latency.
- Для одного запуска должна использоваться одна и та же embedding-модель.

Пример метаданных:

```json
{
  "embedding_provider": "ollama",
  "embedding_model": "qwen3-embedding:4b",
  "embedding_dimension": 2560
}
```

Конкретная размерность должна определяться фактическим ответом модели, а не фиксироваться без проверки.

---

## 8.5. Кластеризация и поиск сценариев

### Основной принцип

Кластеризация выполняется отдельно внутри каждого `task_type`.

Пример:

```text
data_analysis
  ├── Экспорт CRM в Excel
  ├── Анализ продаж
  └── Тендерная отчётность

communication
  ├── Ответ клиенту
  ├── Деловые письма
  └── Отзыв сотруднику
```

Это позволяет формировать более интерпретируемые сценарии и уменьшает вероятность смешивания разных типов задач.

### Алгоритм MVP

1. выбрать записи одного `task_type`;
2. получить embeddings;
3. применить UMAP;
4. применить HDBSCAN;
5. сохранить cluster label;
6. сохранить вероятность принадлежности к кластеру;
7. определить выбросы;
8. сформировать стабильный `scenario_id`.

### Воспроизводимость

UMAP должен использовать фиксированный `random_state`.

Все параметры UMAP и HDBSCAN должны сохраняться в метаданных запуска.

### Малые группы

Если внутри `task_type` недостаточно записей для HDBSCAN:

- не запускать алгоритм с заведомо некорректными параметрами;
- использовать fallback-сценарий;
- явно отметить низкую статистическую надёжность.

Пример fallback:

```json
{
  "scenario_id": "data_analysis:small_group",
  "scenario_name": "Прочие запросы анализа данных",
  "cluster_method": "small_group_fallback",
  "statistical_reliability": "low"
}
```

## 8.6. Выбросы и нетипичные запросы

HDBSCAN label `-1` означает, что запрос не вошёл в устойчивый плотный кластер.

Это не является доказательством того, что ИИ-агент ошибся или не справился.

В результате должны использоваться поля:

```json
{
  "is_outlier": true,
  "outlier_score": 0.87
}
```

На дашборде такие записи должны называться:

```text
Нетипичные или редкие запросы
```

Запрещается автоматически называть их:

```text
Ошибки агента
```

без дополнительных сигналов качества.

## 8.7. Анализ проблем и ошибок агента

Анализ проблем агента выполняется только при наличии релевантных полей:

- `response_status`;
- `error_code`;
- `response_text`;
- `user_feedback`;
- `retry_count`;
- `response_latency_ms`;
- иных согласованных сигналов.

Пример результата:

```json
{
  "has_failure_signals": true,
  "failure_signals": [
    "tool_error",
    "negative_feedback",
    "multiple_retries"
  ],
  "failure_score": 0.84
}
```

Если таких данных нет:

```json
{
  "failure_analysis": {
    "status": "not_available",
    "reason": "Response, feedback and technical failure signals were not provided"
  }
}
```

Допускается вычислять эвристический `potential_problem_score`, но его необходимо обозначать как предположение, а не подтверждённую ошибку.

## 8.8. Саммаризация сценариев

Для каждого сценария необходимо выбрать репрезентативные запросы.

Рекомендуемый вариант:

1. рассчитать centroid кластера;
2. выбрать ближайшие к centroid записи;
3. при возможности добавить несколько граничных формулировок;
4. удалить дубликаты;
5. отправить репрезентативный набор в LLM.

LLM должна возвращать структурированный JSON, а не свободный текст.

Обязательные поля сценария:

```json
{
  "scenario_id": "data_analysis:cluster_01",
  "task_type": "data_analysis",
  "name": "Экспорт отчётов CRM",
  "summary": "Пользователи выгружают данные из CRM и формируют таблицы для последующего анализа.",
  "user_goal": "Быстро получить структурированную отчётность без ручной выгрузки.",
  "representative_examples": [
    "Выгрузи список выигранных тендеров",
    "Собери отчёт по продажам за неделю",
    "Экспортируй данные клиента в Excel"
  ],
  "pain_points": [
    "Ручной сбор информации из нескольких систем",
    "Повторяющиеся операции экспорта"
  ],
  "automation_potential": "high"
}
```

### Ограничения

- `name` должен содержать не более четырёх слов.
- `summary` должен быть коротким и предметным.
- Название не должно быть рекламным или абстрактным.
- LLM не должна придумывать факты, отсутствующие в примерах.
- Ответ LLM должен валидироваться Pydantic-схемой.
- При невалидном ответе допускается ограниченное число повторов.
- При полном отказе LLM должен использоваться fallback с техническим названием.

Пример fallback:

```text
Сценарий data_analysis 01
```

## 8.9. Расчёт трендов

Тренд рассчитывается только при наличии корректных временных меток.

### Правило MVP

1. определить минимальную и максимальную дату внутри batch;
2. разделить период на две равные части;
3. посчитать количество запросов сценария в первой части;
4. посчитать количество запросов сценария во второй части;
5. вычислить процент изменения.

Пример:

```text
previous_count = 100
current_count = 120
growth_rate_percent = 20
```

Классификация:

```text
growth_rate_percent > +10%  -> up
growth_rate_percent < -10%  -> down
иначе                       -> stable
```

Если в одном из периодов недостаточно данных:

```json
{
  "trend": "insufficient_data",
  "growth_rate_percent": null
}
```

Если `previous_count = 0`, процент роста не должен вычисляться стандартным делением.

Допустимый результат:

```json
{
  "trend": "new",
  "growth_rate_percent": null
}
```

Параметры порога и минимального числа записей должны быть конфигурируемыми.

## 8.10. Агрегация для дашборда

Лимиты берутся из `pipeline_config`, а при отсутствии оттуда — из `config.yaml`.

### Задачи: Top N + Other

1. подсчитать частоту всех `task_type`;
2. отсортировать по убыванию;
3. взять первые `top_tasks_limit`;
4. остальные категории суммировать в:

```json
{
  "task_type": "other",
  "count": 10
}
```

Категория `unknown` должна сохраняться отдельно и не сливаться с `other`, если она входит в Top N либо если продуктовая команда требует обязательного отображения качества классификации.

### Сценарии: Top N + Other

1. посчитать число запросов в каждом сценарии;
2. отсортировать по убыванию;
3. взять первые `top_scenarios_limit`;
4. остальные сценарии суммировать в:

```json
{
  "scenario_id": "other",
  "name": "Другие сценарии",
  "count": 150
}
```

Для агрегированного `other` не следует генерировать искусственное summary от LLM.

### Динамика

Минимальный вариант:

```json
[
  {
    "date": "2026-07-23",
    "count": 800
  },
  {
    "date": "2026-07-24",
    "count": 1000
  }
]
```

### Выбросы

```json
{
  "total_outliers_count": 45,
  "outlier_percentage": 4.5
}
```

### Анализ проблем

Если сигналы доступны:

```json
{
  "total_requests_with_failure_signals": 30,
  "failure_signal_percentage": 3.0,
  "top_failure_signals": [
    {
      "signal": "tool_error",
      "count": 12
    }
  ]
}
```

Если недоступны:

```json
{
  "status": "not_available"
}
```

- `schema_version`;
- `pipeline_version`;
- `taxonomy_version`;
- версия модели классификатора;
- embedding provider и model;
- LLM provider и model;
- параметры UMAP;

Изменение набора категорий должно сопровождаться изменением `taxonomy_version`.

## 13. Evaluation

Evaluation является обязательной частью ML-сервиса, но не должна блокировать создание первого end-to-end прототипа.

### 13.1. Классификация

Минимальные метрики:

- accuracy;
- macro F1;
- weighted F1;
- confusion matrix;
- coverage при заданном confidence threshold;
- доля `unknown`.

### 13.2. Кластеризация

Минимальные проверки:

- ручная экспертная оценка выборки кластеров;
- cluster purity при наличии разметки;
- доля выбросов;
- устойчивость кластеров при повторном запуске;
- средняя внутрикластерная близость;
- число слишком малых кластеров.

Silhouette Score может использоваться как вспомогательная метрика, но не должен быть единственным критерием качества.

### 13.3. Саммаризация

Минимальная ручная оценка:

- соответствует ли название примерам;
- не смешивает ли разные сценарии;
- не содержит ли выдуманных фактов;
- понятно ли название бизнес-пользователю;
- корректно ли определён automation potential.

### 13.4. Golden set

В `eval/datasets` необходимо создать небольшой размеченный набор:

- запрос;
- ожидаемый `task_type`;
- ожидаемый сценарий или группа;
- допустимые названия сценария;
- наличие или отсутствие failure signals.

Baseline-отчёты не должны автоматически перезаписываться без явного действия разработчика.

## 14. Тестирование

### 14.1. Unit tests

Обязательные области:

- конфигурация;
- JSONL validation;
- taxonomy;
- расчёт трендов;
- Top N + Other;
- разделение `unknown` и `other`;
- long-text chunking;
- атомарная запись результата;
- маппинг provider errors;

- response schema `POST /analyze`;
- status response;

### 15.1. Volume

```yaml
volumes:
  - prompt_radar_data:/data
```

Backend и ML-сервис должны видеть один и тот же logical path:

```text
/data/runs/{analysis_run_id}/
```

## 18. Definition of Done

ML-сервис считается готовым для hackathon MVP, если:

- сервис запускается через Docker Compose;
- `/health/live` отвечает;
- `/health/ready` корректно отражает готовность;
- Main Backend может запустить анализ;
- повторный запрос не создаёт дубль;
- статус анализа можно получить по API;
- входной JSONL читается потоково;
- длинные запросы не обрезаются молча;
- классификация возвращает класс и confidence;
- низкая уверенность обозначается как `unknown`;
- кластеризация выполняется внутри типа задачи;
- HDBSCAN-выбросы обозначаются как outliers, а не как ошибки агента;
- сценарии имеют название, summary, user goal и примеры;
- при наличии сигналов рассчитывается failure analysis;
- при отсутствии сигналов сервис честно возвращает `not_available`;
- результат записывается атомарно;
- `result.json` проходит schema validation;
- присутствуют технические метрики;
- есть unit, contract, integration и smoke tests;
- README описывает запуск, ограничения и известные компромиссы;
- `make test-ml` и `make smoke` проходят в согласованном окружении.

## 19. Ограничения MVP

В рамках первой версии допускаются следующие ограничения:

- фоновая обработка внутри одного процесса;
- отсутствие распределённой очереди;
- отсутствие горизонтального масштабирования;
- локальный Docker Volume вместо S3/MinIO;
- ограниченный demo dataset;
- ручная подготовка CatBoost model artifact;
- частично ручная оценка кластеров и саммари.

Эти ограничения должны быть явно указаны в README и не должны скрываться от команды или жюри.

## 20. Ключевые архитектурные решения

1. ML-сервис отделён от Main Backend.
2. Большие логи передаются через URI.
3. Контракт версионируется.
4. Длинные запросы обрабатываются явно.
5. Фиктивное обучение CatBoost на семи строках запрещено.
6. Низкая уверенность классификации обозначается как `unknown`.
7. `other` используется только для агрегированного хвоста.
8. Кластеризация выполняется внутри категории.
9. HDBSCAN-выброс не считается подтверждённой ошибкой агента.
10. Ошибки агента определяются только по дополнительным сигналам.
11. Саммаризация возвращает структурированный результат.
12. Итоговый файл записывается атомарно.
13. Первый этап разработки должен дать работающий end-to-end контур на mock pipeline.
