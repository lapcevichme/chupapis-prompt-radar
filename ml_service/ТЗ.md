# Техническое задание — ML-сервис «Промпт-радар»

**Версия:** 2.0 (стриминговый CQRS) · **Статус:** к разработке · **Контур:** hackathon MVP
**Расположение:** `ml_service/`

> Версия 2.0 заменяет ранее описанный file-based analysis-run. Причина и обоснование —
> `docs/decisions/DECISIONS.md` → D1. Контракт с backend — `docs/contracts/backend-ml.md`.

---

## 1. Назначение

ML-сервис принимает поток логов запросов к корпоративным ИИ-агентам, в реальном времени
классифицирует их и назначает в сценарии (кластеры), периодически пересчитывает кластеры и
генерирует их названия, и **мгновенно отдаёт готовую агрегированную аналитику** для дашборда.

Принцип — CQRS: разделение потоков записи, тяжёлого пересчёта и чтения.

- **Write (async):** `PUT /api/v1/logs` — приём батчей → `202` → фоновая классификация +
  эмбеддинг + онлайн-назначение в кластер.
- **Recompute (heavy):** `POST /api/v1/recompute` — UMAP + HDBSCAN + LLM-нейминг. Вручную/по крону.
- **Read (fast):** `GET /api/v1/statistics` (+ `/scenarios`, `/assignments`) — из стора, без ML-вызовов.

## 2. Место в архитектуре и границы

```text
backend  ──PUT /logs──▶  ML  (Qdrant + мета-БД)  ──GET /statistics──▶  backend ──▶ frontend
         ──POST /recompute──▶                    ──GET /assignments──▶
```

**ML отвечает за:** приём и валидацию логов; классификацию по task_type; эмбеддинги;
онлайн-назначение в кластеры; периодический пересчёт (UMAP+HDBSCAN); нейминг и саммари сценариев;
расчёт агрегатов для дашборда; failure-анализ по сигналам; ведение своего стора; технические метрики.

**ML НЕ отвечает за:** пользовательскую авторизацию, загрузку файлов через UI, хранение
бизнес-сущностей приложения, историю ingestion-источников (это backend), **ROI/FTE** (считает
backend), создание frontend-страниц, прямое взаимодействие с frontend.

**Владение стором (D2):** ML владеет **Qdrant** (векторы) + лёгкой мета-БД (SQLite/Postgres:
кластеры, центроиды, имена/саммари сценариев, назначения по `request_id`, агрегаты). ML не
импортирует код `backend`, backend не импортирует код ML.

### Ключевой инвариант ROI

ML отдаёт назначения (`request_id → task_type, scenario_id, is_outlier, has_failure_signals`)
через `GET /assignments`. Сырые ROI-поля (tokens/manual_time/tools) хранит backend — ML их
использовать не обязан.

(async worker в одном процессе, ограничение указать в README).

## 5. Модель данных ML

- **Qdrant collection** `prompt_radar_vectors`: point per `request_id`, payload =
  `{ request_id, task_type, scenario_id, timestamp, source_id, is_outlier, has_failure_signals,
  failure_signals[] }`, vector = эмбеддинг запроса.
- **meta-БД**:
  - `clusters` — `scenario_id`, `task_type`, `centroid`(vector ref), `name`, `summary`,
    `user_goal`, `pain_points`, `automation_potential`, `records_count`, `statistical_reliability`,
    `updated_at`.
  - `ingest_log` (опц.) — счётчики принятых/классифицированных/назначенных по `source_id`.
  - `recompute_jobs` — `job_id`, `status`, `clusters_created`, `scenarios_named`, timestamps.

Кластеризация выполняется **внутри каждого `task_type`** — `scenario_id` формата
`{task_type}:cluster_{n}` (стабильный между пересчётами по составу/центроиду).

## 6. Вход: запись лога

Формат одной записи — `docs/contracts/log.schema.json`. Обязательные: `request_id`, `query_text`,
`timestamp`. Опциональные: `source_id`, `response_status`, `error_code`, `user_feedback`,
`retry_count`, `metadata` (в т.ч. `gold_category` для eval). Идемпотентность по `request_id`.

Валидация: пустой `query_text` (после trim) → reject; некорректный `timestamp` → reject;
невалидные записи не роняют батч (счётчик `rejected`); причины — в метриках/логах.

## 7. API

Префикс `/api/v1`. Health — `/health/*`. Все эндпоинты требуют `X-Service-Token`.
Полные примеры — `docs/contracts/backend-ml.md`.

- `PUT /api/v1/logs` → `202 { accepted, duplicates, rejected, source_id }`. Обработка в фоне.
- `POST /api/v1/recompute` → `202 { job_id, status }`. `GET /api/v1/recompute/{job_id}` → статус.
- `GET /api/v1/statistics` (фильтры `source_id/from/to`) → структура `statistics.schema.json`.
- `GET /api/v1/scenarios` (+ `/{scenario_id}`) → список/детали сценариев.
- `GET /api/v1/assignments` (фильтры + пагинация) → `{ items: [{request_id, task_type,
  classification_confidence, scenario_id, scenario_name, is_outlier, has_failure_signals}], total }`.
- `GET /health/live`, `GET /health/ready`.

## 8. Пайплайн

### 8.1. Предобработка

Нормализация пробелов; сохранение оригинала + нормализованного представления; оценка числа
токенов; определение языка при необходимости; не изменять `request_id`; не удалять значимые
технические конструкции.

### 8.2. Длинные запросы

Средний запрос может быть очень большим (в кейсе — до ~100k токенов). Молчаливое обрезание
запрещено. Если текст > `max_direct_tokens`: перекрывающиеся chunks → извлечь краткое намерение
и ключевые действия → сводное представление → классификация и эмбеддинг по сводке.
Стратегия и факт (`long_text_strategy`, `chunks_processed`) фиксируются в метриках.

### 8.3. Классификация (Трек 1)

CatBoost по эмбеддингу или тексту, из `model_path`. Возвращает `task_type` + `confidence`.
Confidence < порога → `task_type = unknown` (per-record). Таксономия — `docs/taxonomy/taxonomy_v1.md`
(7 классов v1). **Запрещено** обучать фиктивный CatBoost на микро-датасете; при отсутствии
артефакта — режим `fail_fast` (readiness `degraded`, код `CLASSIFIER_NOT_AVAILABLE`) или
`llm_fallback` / `embedding_centroid_fallback` (явно в конфиге и в `pipeline_metadata`).

### 8.4. Эмбеддинги

Через общий интерфейс (Ollama/OpenRouter), provider-specific model IDs, timeout+retry,
ограничение параллелизма, конфигурируемый batch. Ошибки классифицируются retryable/non-retryable.
Одна embedding-модель на весь стор. Размерность определяется фактическим ответом модели.

### 8.5. Онлайн-кластеризация (Трек 2, на каждый лог)

1. получить эмбеддинг; 2. сравнить с центроидами кластеров того же `task_type` (cosine);
3. если max-сходство ≥ `similarity_threshold` → назначить в кластер, пересчитать центроид;
4. иначе → новый кластер `{task_type}:cluster_{n}` (пока без имени);
5. записать point в Qdrant + назначение в мету.

Это даёт мгновенную аналитику, но имена/саммари появляются только после пересчёта.

### 8.6. Пересчёт (Трек 3, heavy, по триггеру/крону)

Для каждого `task_type`: взять векторы → UMAP (фиксированный `random_state`) → HDBSCAN →
стабилизировать `scenario_id` → пересчитать центроиды, `records_count`, outliers → для новых/
изменившихся ядер запустить саммаризацию. Параметры UMAP/HDBSCAN → в `pipeline_metadata`.
Малые группы (недостаточно записей для HDBSCAN) → fallback-сценарий с пометкой
`statistical_reliability: low`, без запуска алгоритма с некорректными параметрами.

### 8.7. Выбросы

HDBSCAN label `-1` → `is_outlier: true` + `outlier_score`. На дашборде — «Нетипичные или редкие
запросы», НЕ «Ошибки агента» (без доп. сигналов качества это не ошибка).

### 8.8. Failure-анализ

Только при наличии сигналов (`response_status`, `error_code`, `user_feedback`, `retry_count`,
`response_latency_ms`). Итог: `has_failure_signals`, `failure_signals[]`, агрегат
`failure_analysis` в `/statistics`. Нет сигналов → `failure_analysis.status = not_available`.
Допускается эвристический `potential_problem_score` с явной пометкой «предположение».

### 8.9. Саммаризация сценариев

Для ядра: центроид → ближайшие ~10 записей (KNN) + несколько граничных → дедуп → LLM возвращает
**структурированный JSON** (валидируется Pydantic): `name` (≤ 4 слов), `summary`, `user_goal`,
`pain_points[]`, `automation_potential`. LLM не выдумывает факты вне примеров. При невалидном
ответе — ограниченные ретраи, затем fallback с техническим именем (`Сценарий {task_type} {n}`).

### 8.10. Тренды

По `timestamp`: разбить период на две половины, сравнить количество записей сценария.
> +10% → `up`, < −10% → `down`, иначе `stable`. `previous_count = 0` → `new`. Недостаточно
данных → `insufficient_data`, `growth_rate_percent = null`. Пороги конфигурируемы.

### 8.11. Агрегация для `/statistics`

Top-N задач + `other` (хвост), Top-N сценариев + `other` (без искусственного summary),
динамика по датам, outliers summary, failure summary. `unknown` не сливается с `other`.
Структура — `docs/contracts/statistics.schema.json`.

## 9. Версионирование

В `pipeline_metadata` ответа `/statistics`: `schema_version`, `pipeline_version`,
`taxonomy_version`, версия классификатора, embedding provider+model, LLM provider+model,

## 10. Ошибки

Коды: `INVALID_REQUEST · INGEST_VALIDATION_FAILED · CLASSIFIER_NOT_AVAILABLE ·
EMBEDDING_PROVIDER_UNAVAILABLE · EMBEDDING_REQUEST_FAILED · LLM_PROVIDER_UNAVAILABLE ·
LLM_RESPONSE_INVALID · CLUSTERING_FAILED · STORE_UNAVAILABLE · RECOMPUTE_FAILED · INTERNAL_ERROR`.
Формат: `{ code, message, retryable, details? }`. Без секретов и stack trace наружу.

## 12. Evaluation

- **Классификация:** accuracy, macro/weighted F1, confusion matrix, coverage при пороге, доля `unknown`.
  Golden set в `eval/datasets` (запрос, ожидаемый task_type, ожидаемая группа, допустимые имена).
- **Кластеризация:** ручная оценка выборки, cluster purity при разметке, доля выбросов,
  устойчивость при повторном пересчёте, средняя внутрикластерная близость, число слишком малых кластеров.
- **Саммаризация:** соответствие имени примерам, отсутствие смешения сценариев и выдуманных фактов,
  понятность бизнесу, корректность automation_potential.

Baseline-отчёты не перезаписываются автоматически.

## 17. Definition of Done (ML MVP)

- Поднимается через docker-compose (с Qdrant); `/health/live` и `/health/ready` корректны.
- `PUT /logs` принимает батчи (202), идемпотентно по `request_id`, обрабатывает в фоне.
- Классификация возвращает task_type + confidence; низкая уверенность → `unknown`.
- Онлайн-назначение в сценарий работает; `POST /recompute` даёт кластеры и имена.
- Кластеризация — внутри task_type; HDBSCAN-выбросы помечены как outliers, а не ошибки агента.
- Failure-анализ считается при наличии сигналов, иначе честно `not_available`.
- `GET /statistics` отдаёт валидную по схеме аналитику мгновенно; `GET /assignments` — назначения.
- Длинные запросы не обрезаются молча; параметры пайплайна — в `pipeline_metadata`.
- Есть unit/contract/integration/smoke; README описывает запуск и ограничения MVP.

## 18. Ограничения MVP

Фоновая обработка в одном процессе (без брокера/горизонтального масштабирования); онлайн-порог

## 19. Ключевые архитектурные решения

1. Стриминговый CQRS (write/recompute/read). 2. ML владеет стором (Qdrant + meta). 3. Онлайн-
назначение по cosine + периодический тяжёлый пересчёт. 4. Кластеризация внутри task_type.
5. Низкая уверенность → `unknown`; `other` — только хвост. 6. Outlier ≠ ошибка агента; ошибки —
только по сигналам. 7. Саммаризация — структурированный JSON. 8. ROI считает backend, не ML.
9. Запрещено фиктивное обучение CatBoost. 10. Контракт `/statistics` версионируется.
