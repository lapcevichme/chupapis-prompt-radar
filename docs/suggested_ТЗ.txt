Техническое задание (ТЗ)
Микросервис аналитики пользовательских запросов к ИИ-агентам («Промпт-радар»)
1. Описание проекта и цели
Разработать бэкенд-микросервис для автоматической аналитики логов диалогов пользователей с корпоративными ИИ-агентами.
Система должна принимать сырые логи, классифицировать их по базовым задачам, выявлять новые сценарии использования (через векторизацию и кластеризацию) и отдавать готовую статистику для отрисовки дашборда.
Решение должно работать без жесткой привязки к мощным GPU (H100), использовать легковесные математические модели на бэкенде и поддерживать переключение нейросетей между локальным контуром (Ollama) и облаком (OpenRouter).
2. Общая архитектура (CQRS)
Сервис строится на принципе разделения потоков записи и чтения:
* Запись (Асинхронный поток): Быстрый прием батчей логов, асинхронная векторизация и онлайн-кластеризация в фоновом режиме.
* Чтение (Синхронный поток): Мгновенная отдача агрегированной статистики из БД для дашборда без вызова ML-моделей.
* Батч-процессинг (Крон): Периодический тяжелый пересчет кластеров (раз в 2 часа) для генерации точных названий сценариев.
3. Конфигурация системы
Управление моделями и гиперпараметрами осуществляется через единый файл config.yaml. Система должна поддерживать бесшовное переключение между провайдерами для работы в условиях отсутствия интернета или ограничений по железу.
server:

 port: 8000
 hdbscan_interval_hours: 2

models:
 embeddings:
   provider: "ollama" # Тумблер: "ollama" | "openrouter"
   model_name: "qwen3-embedding-4b" 
   ollama_url: "http://localhost:11434/api/embeddings"
   openrouter_url: "https://openrouter.ai/api/v1/embeddings"

   provider: "ollama" # Тумблер: "ollama" | "openrouter"
   model_name: "gemma-4-26b-a4b" 
   ollama_url: "http://localhost:11434/api/chat"
   openrouter_url: "https://openrouter.ai/api/v1/chat/completions"

   confidence_threshold: 0.6

clustering:

4. Требования к пайплайну обработки логов
Процесс обработки каждого входящего запроса делится на два параллельных трека.
4.1. Трек 1: Классификация задач (Task Type)
* Инструмент: CatBoostClassifier (работает с эмбеддингами или сырым текстом). Никаких mock-заглушек в архитектуре.
* Логика: Текст запроса классифицируется по жестко заданному списку классов из ТЗ заказчика:
   * text_generation (письма, инструкции)
   * code_help (помощь с кодом)
   * data_analysis (анализ данных, Excel, SQL)
   * education (объяснение/обучение)
   * information_search (поиск/сбор информации)
   * task_management (планирование/задачи)
   * other (нерабочее/общие вопросы/аномалии)
* Инициализация (Cold Start): При старте сервис проверяет наличие файла по пути model_path.
   * Если файл есть — веса загружаются.
   * Если файла нет — инстанцируется чистый CatBoostClassifier и моментально обучается (fit) на зашитом в код микро-наборе из 7 синтетических строк (по одной на каждый класс). Это позволяет пайплайну сразу работать и принимать методы .predict() без ошибок падения, пока не будет подложена полноценно обученная модель.
* Маршрутизация уверенности: Если confidence предсказания модели ниже confidence_threshold, запросу принудительно присваивается класс other.
4.2. Трек 2: Онлайн-кластеризация сценариев (Scenarios)
* Векторизация: Запрос асинхронно отправляется к модели qwen3-embedding-4b (через Ollama или OpenRouter согласно конфигу) для получения вектора.
* Маршрутизация (Косинусное сходство): Вектор сравнивается с центроидами существующих кластеров.
   * Если сходство >= 0.85: Запрос относится к существующему scenario_id. Центроид кластера пересчитывается.
   * Если сходство < 0.85: Формируется новый кластер с новым scenario_id (пока без названия).
4.3. Трек 3: Батч-процессинг и Саммаризация (Глобальный пересчет)
* Триггер: Запускается по расписанию (раз в 2 часа).
* Алгоритм:
   1. Извлекаются все векторы из базы данных.
   2. Применяется UMAP для понижения размерности.
   3. Применяется HDBSCAN для выделения плотных ядер (сохраняется устойчивость к шуму).
* Нейминг кластеров (Саммаризация):
   1. Для каждого выделенного кластера находится математический центр (центроид).
   2. По косинусному расстоянию (KNN) отбираются 10 ближайших запросов-соседей к этому центроиду, чтобы LLM увидела вариативность формулировок.
   3. Эти 10 запросов отправляются в LLM gemma-4-26b-a4b (локально или в облако) с системным промптом для генерации короткого и емкого названия сценария (до 4 слов).
   4. Новые названия сценариев обновляются в БД.
5. Требования к API
* PUT /api/logs
   * Назначение: Прием пачки (батча) новых логов от основного бэкенда.
   * Поведение: Должен возвращать 202 Accepted моментально, передавая обработку в фоновый процесс (Background Tasks), чтобы избежать HTTP-таймаутов при ожидании ответов от нейросетей.
* GET /api/statistics
   * Назначение: Отдача готовой статистики для дашборда (Streamlit / Фронтенд).
   * Поведение: Обращается напрямую в базу данных без вызова ML-моделей. Возвращает распределение процентов по Задачам (top_tasks) и Сценариям (top_scenarios).
6. Технологический стек
* Язык и фреймворк: Python 3.10+, FastAPI.
* ML-инструменты: catboost, numpy, scikit-learn (косинусное сходство), umap-learn, hdbscan.
* Интеграции моделей: Асинхронные HTTP-клиенты (httpx / aiohttp) для Ollama API и OpenRouter API.
